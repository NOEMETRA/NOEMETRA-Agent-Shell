## 7. Risoluzione Rilievi Codex Review (Post-Baseline)

A seguito dell'esecuzione di `codex exec review` (modello `gpt-6.1-terra`), sono stati analizzati e risolti i seguenti rilievi:

1. **Riconoscimento Installazioni Locali nel Setup Wizard (`hermes_cli/setup.py`)**:
   - *Problema*: La condizione `is_existing` considerava solo chiavi remote o token attivi, trattando installazioni locali (Ollama/LM Studio) come nuove installazioni al riavvio del wizard.
   - *Risoluzione*: Aggiornato `is_existing` per riconoscere configurazioni con provider/modello espliciti (`model.provider != "auto"` e `model.default` impostato).
2. **Rimozione Voci Duplicate in `CANONICAL_PROVIDERS` (`hermes_cli/models_catalog_static.py`)**:
   - *Problema*: 5 provider (`lmstudio`, `anthropic`, `openai-codex`, `openai-api`, `gemini`) risultavano duplicati nella tupla statica.
   - *Risoluzione*: Rimosse le occorrenze duplicate mantenendo l'elenco coerente a 52 provider canonici unici.
3. **Flusso di Importazione Modelli nel Setup Locale (`hermes_cli/setup_quick.py`)**:
   - *Problema*: `_keep_imported_model` proponeva il passaggio a "Nous Portal" anche durante la configurazione locale offline.
   - *Risoluzione*: Introdotto `_keep_imported_model_local` che propone coerentemente la scelta tra il modello importato e la configurazione Ollama locale offline.
4. **Isolamento Fixture Test di Provider (`tests/providers/test_profile_home_layers.py`)**:
   - *Problema*: Un leak nello stato di discovery nella fixture `homes` causava la perdita del registro nei test eseguiti in sequenza.
   - *Risoluzione*: Garantita la pre-discovery del registro prima dello snapshot della fixture `homes`, portando la suite `tests/providers/` al 100% di successo (93/93 passati).
5. **Migrazione Automatica Stato Desktop Legacy Con Lock, Scoping e Ignoramento File Singleton (`apps/desktop/electron/main.ts`)**:
   - *Problema*: La modifica di `productName` in `package.json` indirizza Electron verso la nuova directory `userData` (`NOEMETRA Agent Shell`). Una migrazione ingenua prima dell'acquisizione del lock o in istanze isolate (`HERMES_DESKTOP_USER_DATA_DIR` o varianti) poteva causare race condition tra processi concorrenti o inquinare directory isolate. Inoltre, su Linux l'acquisizione del single-instance lock genera file `Singleton*` che facevano apparire la nuova cartella come non vuota, bloccando la migrazione.
   - *Risoluzione*: Implementata `maybeMigrateLegacyDesktopState` eseguita *esclusivamente* dopo l'acquisizione confermata del single-instance lock, vincolata esplicitamente alla variante predefinita (`appNamePascal === 'NoemetraAgentShell'`) ed escludendo lockfile e directory di crash (`Singleton*`, `Crashpad`) nella verifica dello stato preesistente. Aggiornati i test in `product-identity.test.ts` (10/10 passati).
6. **Normalizzazione Endpoint con Trailing Slash (`hermes_cli/setup_quick.py`)**:
   - *Problema*: L'inserimento di un URL con slash finale (es. `http://127.0.0.1:11434/v1/`) causava la generazione errata di `.../v1/v1`.
   - *Risoluzione*: Normalizzazione preventiva con `.strip().rstrip("/")`, garantendo endpoint sempre ben formati in qualsiasi combinazione di input.
7. **Disaccoppiamento Feed Aggiornamenti Desktop (`apps/desktop/electron-builder.config.cjs`, `update-notes.ts`, `update-status.tsx`)**:
   - *Problema*: In assenza di variabile d'ambiente `GITHUB_REPOSITORY`, i pacchetti desktop compilati facevano fallback sull'update feed di `NousResearch/hermes-agent`, rischiando di proporre build upstream anziché NOEMETRA.
   - *Risoluzione*: Impostato il fallback predefinito su `NOEMETRA/NOEMETRA-Agent-Shell` e allineati gli URL delle note di rilascio.
8. **Distinzione Server Ollama Vuoto vs Non Raggiungibile (`hermes_cli/setup_quick.py`)**:
   - *Problema*: Se Ollama era attivo ma senza alcun modello scaricato (`/api/tags` restituisce `[]`), il wizard lo trattava come offline/non rilevato e proponeva un modello predefinito senza avvisare della necessità del download.
   - *Risoluzione*: Distinto esplicitamente il caso di server raggiungibile ma privo di modelli (`models is not None and len(models) == 0`), fornendo chiare istruzioni CLI (`ollama pull <modello>`) prima dell'inizio della sessione.
9. **Inizializzazione Mappatura Modello in Setup Locale (`hermes_cli/setup_quick.py`)**:
   - *Problema*: In configurazioni pulite `model` può essere presente come stringa vuota (`""`). `setdefault("model", {})` non rimpiazzava la stringa, generando `TypeError: 'str' object does not support item assignment`.
   - *Risoluzione*: Sostituito con check esplicito `if not isinstance(config.get("model"), dict): config["model"] = {}`, permettendo il salvataggio immediato e senza errori di `provider`, `base_url` e `default`.
10. **Migrazione Stato Desktop per Tutte le Varianti Supportate (`apps/desktop/electron/main.ts`)**:
    - *Problema*: La funzione di migrazione verificava solo la variante standard (`appNamePascal === 'NoemetraAgentShell'`), escludendo le installazioni `bundled` e `light`. Inoltre, nelle release stabili di upstream, `package.json` manteneva `productName: "Hermes"` per tutte le varianti stabili (standard, bundled, light), per cui Electron salvava la directory utente in `Hermes`.
    - *Risoluzione*: Implementata `legacyDirectoryForVariant()` che risolve la directory sorgente effettiva: verifica prima l'eventuale directory specifica (`HermesLight`, `HermesAgent`) e fa fallback sulla cartella canonica upstream `Hermes`. In questo modo gli utenti che aggiornano da qualsiasi variante stabile preservano integralmente connessioni, profilo attivo e stato della finestra, mantenendo l'isolamento per build isolate (`USER_DATA_OVERRIDE` o `HERMES_DATA_DIR_SUFFIX`).
11. **Preservazione del Placeholder di Versione `0.0.0` in `pyproject.toml` per Compatibilità e Audit di Sicurezza**:
    - *Problema*: Una modifica di `version` in `pyproject.toml` a `0.1.0` alterava il contratto di discovery dell'ambiente virtuale (`_discover_venv`) e i contratti attesi dagli audit di compatibilità/sicurezza descritti in `tests/compat/README.md`.
    - *Risoluzione*: Ripristinato `version = "0.0.0"`. Il versioning applicativo viene governato dai tag di rilascio, da `apps/desktop/package.json` e dai canali di update di NOEMETRA, senza rompere i contratti di security audit sui sorgenti editabili.
12. **Adozione di `prompt_choice` per la Selezione Modelli nel Setup Locale (`hermes_cli/setup_quick.py`)**:
    - *Problema*: L'uso di raw `input()` nel setup rapido per la selezione dei modelli Ollama bypassava il seam ufficiale del wizard con navigazione da tastiera / frecce e supporto per replay / navigazione all'indietro (`prompt_choice`).
    - *Risoluzione*: Sostituito l'input grezzo con `prompt_choice`, consentendo la navigazione interattiva tra i modelli rilevati, l'inserimento manuale di un nome alternativo o la configurazione di un endpoint alternativo.
13. **Flessibilità Endpoint Locale con Selezione Alternativa anche con Ollama Attivo (`hermes_cli/setup_quick.py`)**:
    - *Problema*: Se Ollama rispondeva sulla porta 11434, l'utente non aveva un'opzione diretta per scegliere un server alternativo locale (es. LM Studio su porta 1234, vLLM su 8000).
    - *Risoluzione*: Aggiunta in modo trasparente l'opzione "Configure another local server (LM Studio, vLLM, custom endpoint)..." in tutti i branch di setup locale, configurando automaticamente il provider appropriato (`ollama` o `custom`) e normalizzando l'endpoint base.
14. **Pinning Esplicito del Percorso `userData` per le Release Stabili Desktop (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Nelle build stabili dove `applyDesktopIdentity()` restituiva `null`, l'assenza di un `app.setPath('userData', ...)` esplicito prima di `app.setName()` causava la ri-derivazione implicita di Electron della cartella utente verso il nome applicativo legacy (`Hermes`), rendendo inaccessibile lo stato migrato nella nuova cartella `NOEMETRA Agent Shell`.
    - *Risoluzione*: Aggiunto pinning preventivo con `app.setPath('userData', stableUserData)` prima della migrazione e prima dell'acquisizione del lock, garantendo che lock, migrazione ed esecuzione runtime puntino costantemente alla medesima directory `userData`. Aggiornato inoltre il fallback di `APP_NAME` su `PRODUCT_IDENTITY.displayName`.
15. **Isolamento delle Build Light Non-Stabili dalla Migrazione di Stato (`apps/desktop/electron/main.ts`)**:
    - *Problema*: La condizione `PRODUCT_IDENTITY.light` corrispondeva anche alle build canary o di commit di Light, rischiando di importare lo stato stabile di Hermes in ambienti di test/canary isolati.
    - *Risoluzione*: Rafforzato il controllo con il nome esatto della variante stabile `PRODUCT_IDENTITY.appNamePascal === 'NoemetraLight'`, escludendo in modo rigoroso le build canary e di commit dalla migrazione.
16. **Reset Completo dei Parametri di Trasporto nel Setup Locale (`hermes_cli/setup_quick.py`)**:
    - *Problema*: Quando l'utente importava una configurazione remota (es. OpenAI/Codex con `api_mode: "responses"`) e decideva di configurare un modello locale, l'aggiornamento parziale di `model` manteneva intatto `api_mode` o le intestazioni di autenticazione, causando chiamate con protocolli non supportati verso server Ollama o LM Studio.
    - *Risoluzione*: Invocata `clear_model_endpoint_credentials(model_cfg, clear_api_key=True, clear_api_mode=True)` e rimosse le chiavi di trasporto residue (`wire_format`, `headers`, `extra_body`, `auth_header`), garantendo che il provider locale operi su un endpoint OpenAI-compatible pulito (`/v1/chat/completions`).
17. **Rollback e Recupero della Migrazione Desktop su Fallimento della Destinazione (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il merge da staging a destinazione falliva a metà, i file parzialmente scritti venivano considerati "stato significativo" da un riavvio successivo, bloccando definitivamente il retry della migrazione senza marcatore di completamento.
    - *Risoluzione*: Aggiunta marcatura di lavorazione `.migration-in-progress` e rollback immediato dei file tracciati in caso di eccezione durante il merge (in conformità alla policy per fallimenti di scritture autoritative di `apps/desktop/AGENTS.md`). All'avvio, l'eventuale presenza di un marker in-progress non completato pulisce i residui parziali e riesegue la migrazione in modo trasparente e sicuro.
18. **Supporto alla Migrazione per le Installazioni Canary di Hermes (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Gli utenti di build Canary (`appNamePascal` con suffisso `Canary`) non venivano intercettati dai controlli delle varianti stabili, iniziando con desktop vuoto.
    - *Risoluzione*: Mappate le directory legacy canary corrispondenti (`NoemetraAgentShellCanary` -> `HermesCanary`, `NoemetraAgentShellBundledCanary` -> `HermesBundledCanary` fallback `HermesCanary`, `NoemetraLightCanary` -> `HermesLightCanary` fallback `HermesCanary`), preservando il rigido isolamento di canale tra stabili e canary.
19. **Coordinamento della Migrazione con l'Applicazione Legacy e Consistenza Snapshot Storage (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se l'applicazione Hermes legacy era ancora aperta durante il primo avvio di NOEMETRA, la copia dei file di Chromium `Local Storage` e dei database LevelDB avveniva su file aperti in scrittura, rischiando stati inconsistenti o perdita delle impostazioni del renderer.
    - *Risoluzione*: Implementata `isLegacyAppRunning()` che verifica i lock attivi su `SingletonLock` e sul file `LOCK` di LevelDB (`Local Storage/leveldb/LOCK`). Se l'applicazione legacy è attiva, la migrazione viene posticipata in sicurezza al riavvio successivo a processo chiuso, garantendo la copia esclusiva di snapshot stabili, chiusi e consistenti.
20. **Ispezione Affidabile del Lock Singleton su Linux Senza Risoluzione del Simlink (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Su Linux, il file `SingletonLock` di Chromium è un symlink che punta a `<hostname>-<pid>` (un target non presente nel filesystem). `fs.existsSync` tentava di risolverlo fallendo con `ENOENT` e riportando falsamente il lock come inattivo. Inoltre, l'apertura del file `LOCK` di LevelDB non testa i lock consultivi Unix.
    - *Risoluzione*: Integrata `readlinkSync` che legge direttamente il target del simlink senza seguirlo, estrae il PID del proprietario e ne verifica l'effettiva liveness con `readLinuxProcState` e `isStaleSingletonLockOwner`, rilevando con certezza assoluta lo stato di esecuzione dell'applicazione legacy su Linux e macOS.
21. **Preservazione del Percorso di Retry per Migrazioni Posticipate (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se l'applicazione legacy era aperta al primo avvio di NOEMETRA, la migrazione veniva posticipata, ma l'avvio della shell generava file di configurazione predefiniti in `currentDir`. Al secondo avvio, tali file predefiniti venivano scambiati per "stato utente significativo", bloccando per sempre il recupero dello stato legacy.
    - *Risoluzione*: Introdotto il marcatore `.legacy-migration-pending`: se la migrazione è stata posticipata a causa del processo legacy attivo, un avvio successivo rileva il marcatore di attesa, bypassa i file predefiniti temporanei, completa il merge e rimuove il marcatore pendente garantendo che le impostazioni legacy vengano sempre recuperate.
22. **Ripristino Atomico dello Stato Pre-Esistente in Caso di Rollback della Migrazione (`apps/desktop/electron/main.ts`)**:
    - *Problema*: In caso di migrazione posticipata, l'utente poteva avviare e utilizzare NOEMETRA creando stato locale prima della successiva migrazione. Se la copia da staging falliva, la procedura di rollback rimuoveva incondizionatamente le cartelle corrispondenti presenti in destinazione (incluso `Local Storage`), distruggendo lo stato pre-esistente dell'utente anziché ripristinarlo.
    - *Risoluzione*: Implementato snapshot transazionale preventivo in `.migration-backup`. In caso di eccezione durante il merge, `rollbackMigrationDestination()` ripristina integralmente ogni voce e directory pre-esistente dal backup, rispettando il vincolo di `apps/desktop/AGENTS.md` (L72-L78) che impone il rollback trasparente e sicuro delle scritture autoritative senza perdita di dati.
23. **Migrazione Atomica delle Directory Database LevelDB e Preservazione Modifiche Intermedie (`apps/desktop/electron/main.ts`)**:
    - *Problema*: La copia con `fs.cpSync(..., { force: false })` su una directory `Local Storage/leveldb` pre-esistente (creata dall'avvio temporaneo di NOEMETRA) non sovrascriveva i file collidenti (`CURRENT`, `MANIFEST`), lasciando attivo il database vuoto di default e generando una directory ibrida corrotta con file `.ldb` misti, vanificando la migrazione di connessioni e profili.
    - *Risoluzione*: Identificate le directory di storage atomiche (`DATABASE_DIR_NAMES`: `Local Storage`, `Session Storage`, `IndexedDB` e directory contenenti sottocartelle `leveldb`). Tali cartelle vengono trasferite come unità coerenti indivisibili: l'eventuale directory locale pre-esistente viene prima archiviata in sicurezza come backup (es. `Local Storage.postponed-backup`) per garantire che nessuna modifica utente intermedia venga scartata, e la cartella viene quindi sostituita integralmente dallo snapshot legacy integro e coerente.
24. **Preservazione Non-Distruttiva dei Database Attivi e Riconciliazione Connessioni (`apps/desktop/electron/main.ts`)**:
    - *Problema*: La sovrascrittura incondizionata dei database attivi (`Local Storage`, `IndexedDB`) con lo snapshot legacy causava la perdita di impostazioni e sessioni create dall'utente durante l'utilizzo di NOEMETRA a migrazione posticipata.
    - *Risoluzione*: Se la destinazione possiede già un database attivo, questo viene preservato intatto come sorgente attiva; lo snapshot legacy viene memorizzato a lato (`.legacy`) per consultazione e importazione, mentre i registri `connections.json` vengono riconciliati unendo in modo non distruttivo le connessioni legacy senza alterare il gateway primario configurato in NOEMETRA.
25. **Abort Tutelativo della Migrazione su Fallimento dello Snapshot di Backup (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se la copia di un elemento nel backup preventivo falliva, la procedura proseguiva con snapshot parziale; in caso di errore successivo, il rollback avrebbe rimosso elementi mai salvati nel backup.
    - *Risoluzione*: Implementato controllo rigoroso con ritorno booleano in `backupPreMigrationDestination()`. Se anche un solo elemento non può essere copiato nel backup, la migrazione viene immediatamente abortita prima di modificare `currentDir`, ottemperando alla policy di `apps/desktop/AGENTS.md` (L73-L78).
26. **Ripristino Pulito da Crash con Rimozione Preventiva dei File Parziali Staged (`apps/desktop/electron/main.ts`)**:
    - *Problema*: In caso di crash durante la migrazione prima della scrittura del marker di completamento, la routine di recupero ripristinava il backup senza ripulire i nuovi file parzialmente scritti da staging.
    - *Risoluzione*: In fase di recovery all'avvio, vengono prima rimossi tutti gli elementi staged parziali e successivamente ripristinati gli elementi originari da `.migration-backup`, garantendo che un successivo avvio riparta da uno stato 100% pulito e riproducibile.
27. **Conferma Separata dello Snapshot di Backup Prima di Marcare la Migrazione in Corso (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Scrivere `.migration-in-progress` prima del completamento del backup comportava che un crash durante la fase di copia del backup lasciasse un marcatore di progresso attivo con snapshot incompleto; al riavvio, il rollback eliminava i file di destinazione ripristinando un backup corrotto/incompleto.
    - *Risoluzione*: Introdotto il marker interno `.backup-complete`. Il marcatore `.migration-in-progress` viene ora scritto rigorosamente soltanto DOPO la verifica del completamento integrale del backup. In caso di crash antecedente, la destinazione non è stata modificata e il backup incompleto viene ripulito senza toccare i file utente.

    - *Problema*: Nelle installazioni stabili e canary di Hermes Light e Hermes Bundled, i nomi ufficiali dei pacchetti upstream erano `Hermes Light` e `Hermes Agent` (con spazi). Il controllo cercava solo nomi PascalCase senza spazi, mancando lo stato preesistente e fallendo la migrazione.

29. **Ripristino Intelligente dello Stato Browser e Rilevamento Boilerplate Vuoto (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Durante un avvio a migrazione posticipata, Chromium generava cartelle `Local Storage` e `IndexedDB` vuote di default. Al successivo avvio a Hermes chiuso, la semplice presenza della cartella causava l'archiviazione di legacy in `.legacy` (mai aperto da Electron), impedendo all'utente di recuperare impostazioni del renderer, temi e bozze.
    - *Risoluzione*: Implementata `isDatabaseEmptyOrDefault()` che ispeziona la struttura di LevelDB: se la directory contiene solo metadati minimi di boot senza file tabella `.ldb`, la cartella viene considerata boilerplate temporaneo e sostituita atomisticamente dallo snapshot legacy, ripristinando integralmente le preferenze del renderer; se invece contiene dati utente reali creati nella sessione intermedia, questi vengono preservati in sicurezza prima del ripristino.
30. **Politica 'Merge, Don't Clobber' e Preservazione Attiva del Browser State Posticipato (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Quando l'utente ha prodotto stato attivo nella sessione intermedia, sovrascrivere o archiviare in cartelle cieche faceva sparire le modifiche recenti dell'utente.
    - *Risoluzione*: In ossequio al principio di `apps/desktop/AGENTS.md` (L59-L63), se il database di destinazione contiene dati utente attivi, questo non viene mai sovrascritto; la controparte legacy viene preservata come snapshot consultabile e recuperabile a lato (`.legacy`) corredata da un manifesto autoritativo di recupero `legacy-migration-available.json`.
31. **Trattenuta del Backup e del Marcatore di Recovery su Fallimento del Rollback (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il rollback falliva (es. disco pieno o permessi), il blocco catch ripuliva comunque backup e marcatore in-progress, cancellando permanentemente lo stato utente.
    - *Risoluzione*: `rollbackMigrationDestination` restituisce ora lo stato dell'operazione. Solo se il ripristino dello snapshot di backup è andato a buon fine al 100% vengono ripuliti il backup e il marcatore di progresso; altrimenti entrambi vengono trattenuti intatti per consentire al successivo avvio di completare il ripristino.
32. **Rilevamento Attivo dei Processi Hermes su Windows con Tasklist e Lock Probes (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Su Windows Chromium utilizza named mutex di processo anziché il symlink Unix di `SingletonLock`, e l'apertura del file `LOCK` di LevelDB non testa il byte-range lock `LockFileEx`, consentendo erroneamente a NOEMETRA di copiare database attivi durante la scrittura.
    - *Risoluzione*: Aggiunta scansione attiva dei processi in esecuzione su Windows tramite `tasklist.exe` con filtro CSV (intercettando `Hermes.exe`, `Hermes Agent.exe` e `Hermes Light.exe`) combinata con i probe esclusivi su `SingletonLock` e `LOCK`, garantendo che l'applicazione legacy venga rilevata anche su Windows prima di qualunque operazione di migrazione.
33. **Preservazione Rigorosa dei Database Senza Euristica di Dimensione (`apps/desktop/electron/main.ts`)**:
    - *Problema*: L'analisi basata su log size e ricerca di file `.ldb` poteva scambiare database IndexedDB nidificati per directory vuote o considerare puliti LevelDB con piccoli log, rischiando di clobberare database utente attivi.
    - *Risoluzione*: Sostituita con `isDatabaseVerifiablyEmpty()`, che considera un database sostituibile soltanto se privo di file (`files.length === 0`). Qualunque database presente con contenuti viene rigorosamente lasciato intatto nella sessione attiva, archiviando la controparte legacy in `.legacy` con manifesto di recupero.
34. **Trattenuta dello Snapshot di Backup su Fallimento del Recupero Post-Interruzione (`apps/desktop/electron/main.ts`)**:
    - *Problema*: In caso di crash antecedente con ripristino interrotto o fallito per problemi di I/O o lock all'avvio, gli errori venivano catturati e lo snapshot di backup e il marcatore in-progress venivano comunque eliminati, distruggendo la possibilità di recupero.
    - *Risoluzione*: Il ripristino di ciascun elemento viene verificato e tracciato: `backupDir` e `inProgressPath` vengono rimossi solo se il 100% degli elementi è stato ripristinato con successo; in caso di errore, sia il backup che il marcatore rimangono intatti per i successivi tentativi.
35. **Preservazione della Cartella di Staging su Fallimento del Rollback Immediato (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Il blocco `finally` ripuliva incondizionatamente la cartella di staging anche in caso di fallimento del rollback, privando il recovery ladder all'avvio successivo dell'elenco dei file parzialmente applicati da ripulire.
    - *Risoluzione*: Introdotto il flag `rollbackFailed`: la cartella `.migration-stage` viene trattenuta integra se il rollback non si è concluso con successo, permettendo all'avvio successivo di identificare ed eliminare le voci parziali prima di ripristinare il backup.
36. **Arresto Immediato della Migrazione su Fallimento del Ripristino Post-Interruzione (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il ripristino di una precedente migrazione interrotta falliva, il codice continuava l'esecuzione avviando una nuova migrazione e sovrascrivendo il backup esistente con uno snapshot parzialmente corrotto.
    - *Risoluzione*: In caso di recovery fallito all'avvio, la funzione esegue un `return` immediato senza toccare il backup né tentare una nuova migrazione, preservando intatto lo snapshot per i tentativi successivi.
37. **Ripristino Autoritativo dei Database Browser e Canale IPC di Recupero (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Nei casi di migrazione posticipata, Chromium creava cartelle database con file di default (`CURRENT`, `MANIFEST`); considerare queste cartelle non vuote relegava lo snapshot legacy in `.legacy`, che nessun componente applicativo leggeva, impedendo all'utente di vedere temi, impostazioni e bozze storiche.
    - *Risoluzione*: Il database legacy viene trasferito come unità attiva principale nella destinazione (`Local Storage`, `IndexedDB`), mentre lo stato eventualmente creato nella sessione posticipata viene preservato in `${entry}.intervening`. Sono stati introdotti gli handler IPC `hermes:migration:get-recovery-info` e `hermes:migration:restore-intervening-database` che leggono il manifesto e offrono un percorso di recupero effettivo e invocabile.
38. **Preservazione dell'Eleggibilità alla Migrazione su Fallimenti Transitori (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il primo tentativo di migrazione falliva a causa di errori di I/O o permessi, l'avvio della shell creava file di default; al successivo riavvio `hasMeaningfulState` risultava vero e la migrazione non veniva più riprovata.
    - *Risoluzione*: Il marcatore `.legacy-migration-pending` viene scritto prima dell'inizio delle operazioni di staging, backup e copia, e viene rimosso solo dopo la conferma del completamento integrale, garantendo che qualunque errore transitorio mantenga attiva l'eleggibilità alla migrazione per il riavvio successivo.
39. **Precedenza dell'Intento Utente Attivo e Preservazione Non-Distruttiva dei Database (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Quando la migrazione veniva posticipata per processo legacy attivo, l'utente poteva utilizzare NOEMETRA configurando impostazioni e sessioni. Al successivo avvio a processo legacy chiuso, la migrazione considerava sacrificabile tutto lo stato intermedio sostituendo i database attivi con quelli legacy, causando la sparizione delle modifiche recenti dell'utente.
    - *Risoluzione*: Applicato rigorosamente il principio cardine di `apps/desktop/AGENTS.md` (L59-L64, L75-L78: *merge, don't clobber; newer intent takes precedence*). `hasDatabaseContent()` analizza la presenza di record e tabelle `.ldb` reali nei database attivi: se l'utente ha configurato dati in NOEMETRA, il database attivo (`Local Storage`, `Session Storage`, `IndexedDB`) rimane intatto e non viene toccato; la versione legacy viene preservata come affordance in `.legacy` corredata dal manifesto `legacy-migration-recovery.json`. Se invece la destinazione contiene solo boilerplate vuoto di boot, il database legacy viene ripristinato direttamente come database attivo.
40. **Controllo Rigoroso di Rimozione dei File Staged nel Recupero Post-Interruzione (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Durante il recovery da migrazione interrotta, la rimozione degli elementi staged precedentemente copiati nella destinazione avveniva in un blocco `try/catch` che ignorava gli errori; se un file o cartella parziale non poteva essere rimosso, la procedura proseguiva comunque, fondeva il backup nei file parziali rimasti e cancellava il backup.
    - *Risoluzione*: Introdotto il tracciamento `allStagedRemoved`: se anche una sola rimozione fallisce, l'operazione di recovery fallisce immediatamente, abortendo la procedura e trattenendo integro lo snapshot di backup, la cartella di staging e il marcatore `.migration-in-progress` in conformità alla policy per fallimenti di scritture autoritative.
41. **Canali IPC Unificati di Recupero per Database Legacy e Intermedi (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Mancavano percorsi di recupero bidirezionali invocabili per ripristinare sia snapshot legacy archiviati a lato sia snapshot intermedi salvati durante migrazioni posticipate.
    - *Risoluzione*: Aggiornati e unificati gli handler IPC `hermes:migration:get-recovery-info`, `hermes:migration:restore-legacy-database` e `hermes:migration:restore-intervening-database`, consentendo l'ispezione dei manifesti `legacy-migration-recovery.json` e `legacy-migration-available.json` e offrendo alle interfacce utente e ai tool diagnostici la capacità di ripristinare lo stato desiderato in qualunque scenario di migrazione complessa.
42. **Rilevamento Verificabile dello Stato Database Senza Soglie di Dimensione Arbitrarie (`apps/desktop/electron/main.ts`)**:
    - *Problema*: `hasDatabaseContent()` imponeva una soglia di 1024 byte per i file `.log` di LevelDB; se l'utente creava una quantità modesta di stato durante una migrazione posticipata, il write-ahead log numerato conteneva record validi in meno di 1 KB senza generare file `.ldb`, venendo scambiato per cartella vuota e cancellato.
    - *Risoluzione*: Rimosso ogni cutoff arbitrario di dimensione: qualunque file log numerato (`/^\d+\.log$/i`) con `size > 0` o tabella `.ldb` con `size > 0` o file non standard oltre i metadati di default (`CURRENT`, `LOCK`, `LOG`, `LOG.old`, `MANIFEST-*`) attesta la presenza verificabile di stato utente reale, preservando scrupolosamente le scritture recenti.
43. **Percorso di Recupero Raggiungibile In-App per i Database Legacy Preservati (`apps/desktop/src/store/legacy-migration-recovery.ts`, `apps/desktop/electron/preload.ts`, `apps/desktop/electron/main.ts`)**:
    - *Problema*: Quando i database legacy venivano archiviati a lato (`.legacy`) a causa della presenza di stato utente recente più prioritario, gli handler IPC non erano esposti nel preload né invocati dal renderer, lasciando l'utente privo di un meccanismo grafico per scoprire o ripristinare le preferenze e sessioni storiche.
    - *Risoluzione*: Esposto il bridge `window.hermesDesktop.migration` nel preload e registrato il listener reattivo in `apps/desktop/src/store/legacy-migration-recovery.ts` collegato al toast stack di notifica. All'avvio, se è presente uno snapshot legacy preservato, la shell mostra una notifica interattiva ("Legacy Settings & History Available") che consente all'utente con un solo click di ripristinare lo stato legacy ("Restore Legacy Data") o confermare lo stato corrente ("Keep Current"), ottemperando alla recovery guidance di `apps/desktop/AGENTS.md` (L73-L78).
44. **Rollback Transazionale e Retry su Fallimento della Riconciliazione Connessioni (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se la lettura, il parsing JSON o la scrittura di `connections.json` falliva durante la riconciliazione delle connessioni legacy, l'errore veniva silenziato nel `catch` e la migrazione veniva comunque registrata come completata, omettendo permanentemente le connessioni legacy senza possibilità di retry.
    - *Risoluzione*: Il fallimento genera preventivamente una copia di riserva `connections.legacy.json` ed effettua la propagazione esplicita dell'eccezione (`throw err`). Il chiamante esegue il rollback della transazione tramite `rollbackMigrationDestination`, preservando intatti staging, backup e marcatore pendente per consentire il retry al successivo avvio in piena conformità alle regole sulle scritture autoritative.
45. **Sostituzione Atomica dei Database Pre-Inizializzazione Chromium e Protezione Live Session (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Il ripristino immediato dei database storici tramite IPC rimuoveva e riscriveva la cartella LevelDB mentre Chromium era in esecuzione con file lock aperti, rischiando errori di I/O (`EBUSY`), corruzione di memoria e sovrascritture concorrenti durante il reload.
    - *Risoluzione*: Implementato il pattern di staged replacement con coordinate restart: il click su "Restore Legacy Data" scrive una richiesta transazionale in `.legacy-restore-pending.json` e riavvia l'applicazione con `relaunchApp()`. La funzione `applyPendingLegacyDatabaseRestore()` viene eseguita prima di `app.whenReady()` e prima di qualunque inizializzazione di Chromium: archivia preventivamente il database corrente in `.intervening`, copia lo snapshot legacy pulito, e in caso di errore esegue il rollback automatico da `.intervening`, eliminando qualsiasi conflitto a runtime.
46. **Manifesto Multi-Database e Preservazione Aggregata per Recovery Affordance (`apps/desktop/electron/main.ts`, `apps/desktop/src/global.d.ts`)**:
    - *Problema*: Quando più cartelle database contenevano stato (es. `Local Storage` e `Session Storage`), la scrittura del manifesto in ciascuna iterazione sovrascriveva il file `legacy-migration-recovery.json`, rendendo recuperabile soltanto l'ultimo database processato.
    - *Risoluzione*: Il manifesto raccoglie ora un array completo `databases` con tutti i database preservati (`Local Storage`, `Session Storage`, `IndexedDB`), consentendo all'affordance in-app e agli handler IPC di ripristinare contestualmente l'intero ecosistema di storage storico o singoli database selezionati.
47. **Offerta Universale della Migrazione e del Merge Anche in Presenza di Stato Esistente (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Il controllo `if (!hasMeaningfulState)` escludeva incondizionatamente la migrazione per le installazioni dove la cartella utente era già stata creata o utilizzata prima della migrazione, impedendo il recupero delle connessioni e la preservazione dello storico di Hermes.

Essendo l'algoritmo di migrazione intrinsecamente non distruttivo (preserva lo stato utente attivo, unisce le connessioni e archivia i database legacy come recovery affordance), la procedura viene sempre offerta ed eseguita finché il marcatore `.migration-complete` non certifica la conclusione positiva del processo.
48. **Preservazione dello Snapshot Intermedio Tramite Backup Temporaneo Isolato (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Quando veniva invocato il ripristino del database intermedio (`restoreInterveningDatabase`), `legacyPath` coincideva con `interveningPath`; la routine di swap eliminava `interveningPath` prima di copiare, distruggendo permanentemente lo snapshot intermedio e registrando un ripristino vuoto.
    - *Risoluzione*: Introdotta la cartella di backup temporaneo isolata `.swap-backup-${Date.now()}`: l'aggiornamento di `interveningPath` viene eseguito solo quando la sorgente non è lo snapshot intermedio stesso, garantendo che il ripristino di `.intervening` non distrugga mai la sorgente e consentendo un rollback integro in caso di fallimento.
49. **Preservazione delle Connessioni Legacy Distinte con ID Collidenti (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Due installazioni con etichette identiche (es. `local` o `my-server`) generavano ID identici; la riconciliazione scartava la connessione legacy collidente anche se puntava a un endpoint, host o tipologia di backend completamente differente.
    - *Risoluzione*: Implementata `areConnectionsEquivalent()` per confrontare URL, host, porta, username e profilo. Se due connessioni collidono nell'ID ma presentano configurazioni distinte, alla connessione legacy viene assegnato un nuovo ID univoco (`<id>-legacy`) ed etichetta distinta, conservando integralmente tutte le connessioni senza perdite.
50. **Propagazione del Fallimento Scrittura del Manifesto di Recovery (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se la scrittura del manifesto `legacy-migration-recovery.json` falliva (es. disco pieno o permessi), il blocco `catch` silente consentiva la scrittura del marcatore di completamento e l'eliminazione del backup, lasciando i database in `.legacy` senza affordance grafica e senza retry.
    - *Risoluzione*: L'eccezione viene ora propagata esplicitamente (`throw manifestErr`), attivando il rollback della destinazione tramite `rollbackMigrationDestination`, trattenendo lo snapshot di backup e staging, e garantendo che la migrazione venga ritentata al riavvio successivo.
51. **Confronto Completo dei Campi di Instradamento delle Connessioni (`apps/desktop/electron/main.ts`)**:
    - *Problema*: `areConnectionsEquivalent` utilizzava `type`, `username` e `profile` anziché i campi effettivi di `RegistryConnection` (`kind`, `user`, `remoteProfile`, `keyPath`, `remoteHermesPath`, `org`, `name`), rischiando di scartare connessioni SSH o Cloud distinte che differivano per utente o profilo remoto.
    - *Risoluzione*: Aggiornato il confronto su tutti i campi reali di instradamento del registro (`kind`, `url`, `host`, `port`, `user`/`username`, `remoteProfile`/`profile`, `keyPath`, `remoteHermesPath`, `org`, `name`). Qualunque discrepanza preserva la connessione legacy assegnando un ID univoco incrementale.
52. **Ripristino Bidirezionale dello Stato Intermedio Preservato Post-Restart (`apps/desktop/electron/main.ts`, `apps/desktop/src/store/legacy-migration-recovery.ts`)**:
    - *Problema*: Una volta ripristinati i dati legacy, la rimozione del manifesto impediva all'utente di invertire l'operazione per recuperare le impostazioni o cronologia NOEMETRA create prima dello swap, lasciando i database `.intervening` privi di un'affordance grafica.
    - *Risoluzione*: Al termine della sostituzione prima dell'avvio di Chromium, `applyPendingLegacyDatabaseRestore()` genera un manifesto attivo `status: 'intervening-preserved-legacy-active'` che elenca le directory `.intervening`. All'avvio, la shell mostra la notifica interattiva "Legacy Data Restored" con l'azione "Restore Previous Setup" (che invoca `restoreInterveningDatabase('all')`) e "Keep Legacy" per confermare definitivamente la configurazione storica.
53. **Persistenza della Notifica di Recovery su Fallimento della Richiesta (`apps/desktop/src/store/legacy-migration-recovery.ts`)**:
    - *Problema*: Se la chiamata di staging falliva (es. directory protetta da scrittura), l'errore veniva ignorato e il callback `onDismiss` rimuoveva il manifesto, precludendo ulteriori tentativi di recupero.
    - *Risoluzione*: Rimossa la rimozione preventiva in `onDismiss` e verificato il responso dell'operazione: in caso di fallimento (`res?.ok === false`), viene emessa una notifica di errore descrittiva e il manifesto di recovery viene conservato intatto consentendo all'utente di ritentare.
54. **Transazione Persistita di Swap con Tracciamento Intento 'in_progress' e Ripristino Senza Perdite (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se la copia di uno snapshot falliva dopo la rimozione del database attivo o se il processo veniva interrotto prima della registrazione dello swap completato, la procedura di rollback considerava il database non toccato ed eliminava il backup, causando la perdita irreparabile delle impostazioni o cronologia attiva.
    - *Risoluzione*: Lo stato `db.state = 'in_progress'` viene ora registrato su `.legacy-restore-tx.json` prima della rimozione della directory attiva. In caso di fallimento o crash, sia il rollback immediato che la routine di recupero al riavvio ripristinano dal backup qualunque database toccato (`in_progress` o `swapped`), e il file di backup viene eliminato solo dopo l'effettivo successo del ripristino.
55. **Preservazione dei Backup di Recovery e Transazione su Fallimento di Rollback (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il ripristino di un database dal backup falliva durante il recupero post-crash (es. per permessi o lock transitori), il ciclo rimuoveva comunque il backup e il blocco `finally` cancellava `.legacy-restore-tx.json`, eliminando l'unica copia integra dello stato utente e precludendo tentativi successivi.
    - *Risoluzione*: Il backup e il marcatore di transazione `.legacy-restore-tx.json` vengono ora preservati integralmente a meno che ogni singolo ripristino non si concluda con successo, garantendo la riesecuzione automatica al boot successivo come richiesto da AGENTS.md:73-78.
56. **Tolleranza per i Database Legacy Vuoti nella Migrazione Iniziale (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se un'installazione precedente presentava un database del browser vuoto (es. Session Storage o IndexedDB contenente solo i file di configurazione iniziali di LevelDB senza dati utente), la verifica `hasDatabaseContent()` generava un'eccezione annullando l'intera migrazione e impedendo l'importazione di impostazioni e connessioni valide.
    - *Risoluzione*: La creazione del sidecar `.legacy` viene ora condizionata a `hasDatabaseContent(stagedPath)`: se il database legacy è vuoto, lo stato attivo di destinazione viene preservato intatto senza creare sidecar inutili o generare errori, e la verifica della copia staged controlla la corretta creazione dei file senza imporre la presenza di record utente in database legittimamente vuoti.
57. **Transazione 'committed' e Pubblicazione Manifesto Prima della Pulizia dei Backup (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il processo si interrompeva durante la pulizia dei backup, la transazione rimaneva in stato `swapping` con alcuni backup già eliminati; al riavvio, il recupero tentava il rollback parziale lasciando uno stato database incoerente e non pubblicando l'affordance grafica di recovery.
    - *Risoluzione*: La transazione viene ora marcata `phase: 'committed'` prima di pubblicare il manifesto `legacy-migration-recovery.json`. La pulizia dei backup e la rimozione dei marcatori pendenti avvengono solo a manifesto pubblicato. In caso di interruzione durante o dopo `committed`, il recupero iniziale finalizza la pubblicazione del manifesto e la pulizia senza eseguire rollback.
58. **Blocco dell'Avvio Applicativo in Caso di Rollback Interrotto Incompleto (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il rollback di una transazione interrotta falliva al riavvio (es. per file lock o permessi), il metodo terminava con un semplice log consentendo a Chromium di avviarsi e modificare i database parzialmente ripristinati; al successivo riavvio, il retry avrebbe sovrascritto tali nuove modifiche.
    - *Risoluzione*: In caso di rollback fallito (`!allRollbacksSucceeded`), l'applicazione emette una finestra diagnostica modale e termina immediatamente il processo con `app.exit(1)`, impedendo categoricamente a Chromium di aprire o alterare database in stato incoerente fino alla risoluzione del problema.
59. **Interruzione dell'Avvio se il Rollback della Migrazione Iniziale Fallisce (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il rollback della migrazione falliva (es. durante un errore di copia o durante il recovery all'avvio), l'eccezione veniva catturata a livello globale consentendo l'avvio della shell con una directory parzialmente migrata; al successivo avvio, il recupero avrebbe cancellato i nuovi dati generati durante quella sessione.
    - *Risoluzione*: Sia in caso di rollback fallito durante la copia che in caso di recovery fallito all'avvio, l'applicazione emette una finestra di avviso modale e termina immediatamente con `app.exit(1)`, proteggendo la cartella utente e garantendo che nessun dato venga alterato prima del ripristino sicuro.
60. **Arresto Preventivo dell'Avvio in Caso di Fallimento Scrittura 'committed' (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se la scrittura dello stato `committed` su `.legacy-restore-tx.json` falliva dopo lo swap dei database, l'eccezione veniva catturata esternamente e Chromium si avviava con i database scambiati; al boot successivo, la transazione ancora in stato `swapping` avrebbe eseguito il rollback cancellando le modifiche della sessione.
    - *Risoluzione*: La scrittura di `phase: 'committed'` viene verificata esplicitamente: se fallisce, l'avvio viene arrestato immediatamente con `app.exit(1)` per prevenire la corruzione transazionale.
61. **Preservazione della Transazione e dei Backup se la Pubblicazione del Manifesto Fallisce (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se la scrittura del manifesto di recupero `legacy-migration-recovery.json` falliva, la procedura proseguiva comunque eliminando i backup e il marcatore di transazione, lasciando i database `.intervening` privi di un'affordance grafica per il ripristino.
    - *Risoluzione*: Se la pubblicazione del manifesto fallisce, la transazione `committed` e i file di backup vengono trattenuti intatti; al riavvio successivo, la fase iniziale `STEP 0` rileva lo stato `committed` e ritenta la pubblicazione del manifesto prima di procedere alla pulizia.
62. **Esecuzione del Recupero delle Migrazioni Interrotte Prima del Controllo dell'App Legacy (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se NOEMETRA veniva interrotto durante la migrazione e al riavvio successivo l'applicazione legacy Hermes risultava in esecuzione, il controllo `isLegacyAppRunning()` causava un ritorno anticipato bypassando il recupero dello snapshot di backup; NOEMETRA si avviava quindi su uno stato parziale e corrotto.
    - *Risoluzione*: Il controllo e il ripristino dell'eventuale migrazione interrotta (`inProgressPath`) sono stati posizionati prima della verifica dello stato di Hermes, assicurando che la directory di destinazione venga sempre ripristinata allo stato integro di backup prima di qualsiasi decisione di rinvio.
63. **Confronto Completo delle Credenziali e Headers in `areConnectionsEquivalent` (`apps/desktop/electron/main.ts`)**:
    - *Problema*: La deduplicazione delle connessioni con ID collidenti ignorava `token` e `headers`, scartando connessioni con lo stesso endpoint ma credenziali, account o scope di accesso differenti.
    - *Risoluzione*: Aggiornato il controllo di equivalenza per verificare `token` e `headers`. Connessioni con medesimo URL ma diverse credenziali vengono ora considerate distinte e preservate con ID dedicato.
64. **Migrazione dell'Identità della Partizione OAuth per Connessioni Rinominate (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Assegnando un nuovo ID (`<id>-legacy`) a una connessione legacy collidente, i cookie di sessione OAuth rimanevano nella cartella della partizione legata al vecchio ID, disconnettendo la connessione migrata e rischiando conflitti con la connessione attiva.
    - *Risoluzione*: Implementata `migrateConnectionOauthPartition()` che clona la partizione isolata `Partitions/hermes-remote-oauth-conn-<oldId>` (o dal jar condiviso se era primary legacy) in `Partitions/hermes-remote-oauth-conn-<newId>`, garantendo la continuità immediata del login e l'integrità delle sessioni OAuth secondo AGENTS.md:68-71.
65. **Recupero delle Migrazioni Interrotte Indipendente dall'Esistenza della Directory Legacy (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se l'applicazione veniva interrotta a metà migrazione e la directory legacy Hermes veniva successivamente rimossa, rinominata o spostata, il blocco di recovery veniva ignorato poiché vincolato a `fs.existsSync(legacyDir)`. Chromium si avviava quindi su una destinazione parziale nonostante la presenza del marcatore e del backup completato.
    - *Risoluzione*: La procedura di recupero e rollback delle migrazioni interrotte (`inProgressPath`) è stata disaccoppiata e posizionata prima del controllo di esistenza di `legacyDir`, garantendo che lo stato di destinazione venga sempre ripristinato dal backup locale anche se la sorgente legacy è stata eliminata.
66. **Supporto Completo delle Connessioni OAuth di Tipo 'cloud' nella Riconciliazione del Registro (`apps/desktop/electron/main.ts`)**:
    - *Problema*: La migrazione e preservazione delle partizioni di sessione OAuth era limitata alle sole connessioni `kind === 'remote'`, escludendo le connessioni `kind === 'cloud'` e provocando la perdita della sessione salvata quando una connessione cloud legacy veniva importata come secondaria o rinominata per collisione di ID.
    - *Risoluzione*: Esteso il routing e la clonazione della partizione OAuth a tutte le connessioni con autenticazione OAuth (`kind === 'remote' || kind === 'cloud'`), sia nel ramo di importazione ordinaria da primary legacy che nel ramo di ridenominazione per collisione di ID.
67. **Riconciliazione del Marcatore di Completamento durante il Rollback di Recovery (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se un'interruzione anomala o un fallimento si verificava durante la finalizzazione della migrazione dopo la creazione del file marcatore `.migration-complete`, la procedura di rollback o il recupero all'avvio successivo (`recoverySucceeded`) ripristinavano la destinazione al suo snapshot pre-migrazione senza rimuovere `.migration-complete`. Di conseguenza, i successivi avvii della shell consideravano la migrazione già ultimata, escludendo definitivamente i dati legacy rimasti non migrati.
    - *Risoluzione*: Sia in `rollbackMigrationDestination()` che nel blocco `recoverySucceeded` all'avvio in `STEP 0`, il file `.migration-complete` viene rimosso incondizionatamente insieme a backup e staging. In questo modo lo stato di destinazione torna fedelmente e coerentemente alla situazione pre-migrazione, consentendo il regolare riesame e il completamento della migrazione all'avvio successivo.
68. **Ripristino Transazionale e Pulizia di Database Non Pre-Esistenti nel Rollback (`apps/desktop/electron/main.ts`)**:
    - *Problema*: In `applyPendingLegacyDatabaseRestore()`, se un database di destinazione non esisteva prima del tentativo di swap (`activeExistedInitially: false`), non veniva creato alcuno snapshot in `db.backupPath`. Qualora la transazione fallisse a metà operazione (`!allSucceeded`) o venisse interrotta durante la fase `swapping`, la logica di rollback tentava il ripristino solo per i database con backup esistente (`fs.existsSync(db.backupPath)`). La directory del database toccato rimaneva così creata e popolata nella destinazione attiva, violando il principio di atomicità e rollback transazionale.
    - *Risoluzione*: La transazione traccia ora esplicitamente `activeExistedInitially` per ciascun database. Sia durante il rollback immediato che nel recovery post-crash all'avvio (`STEP 0`), se il database è stato toccato (`wasTouched`) e `!db.activeExistedInitially`, la directory `db.activePath` creata viene rimossa completamente (`fs.rmSync(db.activePath, { recursive: true, force: true })`), ripristinando in modo verificabile e deterministico lo stato originale.
69. **Preservazione e Unione delle Entries Quarantined nel Registro Connessioni (`apps/desktop/electron/main.ts`)**:
    - *Problema*: In `reconcileConnectionsRegistry()`, l'unione del file `connections.json` tra legacy e destinazione riconciliava unicamente la lista `connections`, ignorando il campo `quarantined`. Se il registro storico Hermes conteneva connessioni corrotte o malformate parcheggiate in quarantena, queste venivano perse se la destinazione disponeva già di un file `connections.json` v2.
    - *Risoluzione*: Aggiunta la riconciliazione esplicita per `legacyRegistry.quarantined`: se presente, le entries vengono deduplicate e unite all'array `currentRegistry.quarantined` nel rispetto del massimale `REGISTRY_QUARANTINE_CAP = 20` (come definito in `apps/desktop/electron/connection-registry.ts`), salvaguardando il materiale grezzo di connessione dell'utente senza rischiare la crescita incontrollata del registro.
70. **Trattenimento Atomico dei Backup di Rollback fino al Successo Complessivo del Ripristino (`apps/desktop/electron/main.ts`)**:
    - *Problema*: In caso di ripristino multi-database interrotto o fallito, la rimozione immediata del file di backup di ciascun database appena ripristinato esponeva al rischio di perdita irreversibile di dati: se il ripristino di un database successivo falliva, il primo database restava registrato come toccato nel file di transazione ma privo del suo snapshot di backup. Al boot successivo, la logica di recovery tentava di risincronizzarlo rimuovendo i file attivi senza poterli ripristinare.
    - *Risoluzione*: Sia in `STEP 0` che nel blocco `!allSucceeded` di `applyPendingLegacyDatabaseRestore()`, tutti i file di backup vengono trattenuti intatti fino alla conferma del successo di ogni singolo ripristino (`allRollbacksSucceeded`). Inoltre, lo stato `db.state = 'pending'` viene persistito atomicamente su `.legacy-restore-tx.json` al termine del ripristino di ogni database, garantendo la totale idempotenza e l'eliminazione dei backup solo a transazione ultimata secondo i vincoli di `AGENTS.md:73-78`.
71. **Preservazione della Partizione OAuth Condivisa per Connessioni di Tipo 'cloud' (`apps/desktop/electron/main.ts`)**:
    - *Problema*: `resolveOauthPartition` instrada per architettura tutte le connessioni di tipo `cloud` attraverso la partizione condivisa legacy `hermes-remote-oauth`. Se durante l'importazione di una connessione cloud primaria legacy i cookie venivano clonati su una partizione privata (`hermes-remote-oauth-conn-<id>`), tale partizione non veniva mai interrogata a runtime, determinando la disconnessione e la perdita della sessione autenticata.
    - *Risoluzione*: Corretta la politica di partizionamento: le partizioni dedicate vengono generate e migrate esclusivamente per connessioni `kind === 'remote'` con autenticazione OAuth; per le connessioni `kind === 'cloud'`, `ensureSharedOauthPartitionPreserved()` garantisce che la partizione condivisa `Partitions/hermes-remote-oauth` (interrogata nativamente dal router di sessione) venga preservata e sincronizzata fedelmente dalla sorgente legacy.
72. **Isolamento dei Confini di Account e Riconciliazione Quarantena per Sessioni Cloud OAuth Concorrenti (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Quando sia l'installazione corrente che quella legacy dispongono di una sessione OAuth cloud attiva nella partizione condivisa `hermes-remote-oauth`, l'aggiunta automatica di una connessione cloud OAuth legacy al registro di destinazione avrebbe indotto tale connessione a utilizzare silenziosamente l'account già loggato nella destinazione, violando l'isolamento dei confini di account prescritto da `AGENTS.md:45-47`.
    - *Risoluzione*: In `reconcileConnectionsRegistry()`, se la destinazione dispone già di una partizione `hermes-remote-oauth` attiva e la sorgente legacy possiede a sua volta una sessione cloud, i cookie legacy vengono archiviati come sidecar `hermes-remote-oauth.legacy` (prevenendone la perdita definitiva) e la connessione cloud legacy viene instradata in `currentRegistry.quarantined` con causale `cloud-oauth-account-boundary-reauth-required`. In questo modo la configurazione viene preservata integralmente senza consentire l'accesso con l'account errato ed esigendo una riautenticazione esplicita.
73. **Persistenza dello Stato di Incompletezza per Database con Rollback Fallito (`apps/desktop/electron/main.ts`)**:
    - *Problema*: In caso di operazione interrotta di swap o restore, se un database precedentemente esistente risultava privo del file di backup (`backupPath` assente o corrotto), la routine di rollback rimuoveva la directory attiva e impostava `allRollbacksSucceeded = false`, ma aggiornava erroneamente lo stato del database a `pending` sul file di transazione persistito. Al riavvio successivo, il database non veniva più rilevato come toccato (`wasTouched = false`), provocando l'eliminazione prematura della transazione e l'avvio della shell con il database mancante.
    - *Risoluzione*: Sia in `STEP 0` che nel ramo `!allSucceeded` di `applyPendingLegacyDatabaseRestore()`, lo stato `db.state = 'pending'` viene persistito atomicamente su `.legacy-restore-tx.json` unicamente se il ripristino effettivo dal backup si è concluso con successo (`dbRestored = true`). Se il ripristino fallisce o il backup è assente, lo stato rimane marcato come toccato/incompleto, impedendo la chiusura erronea della transazione in conformità all'invariante di failed-write recovery di `AGENTS.md:75-78`.
74. **Preservazione delle Connessioni OAuth Distinte in Caso di Collisione di ID ed Endpoint (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Se il registro corrente e quello legacy contenevano la medesima connessione remota OAuth (stesso ID ed endpoint URL) ma associata ad account utente differenti, `areConnectionsEquivalent` le considerava identiche poiché le credenziali OAuth risiedono nelle partizioni dei cookie anziché nel file `connections.json`. La connessione legacy veniva scartata, impedendo all'utente di selezionare il proprio account storico.
    - *Risoluzione*: Aggiornata `reconcileConnectionsRegistry()`: quando un ID collidente presenta partizioni di sessione OAuth attive sia nella sorgente che nella destinazione (`hasPotentialOauthAccountCollision`), l'equivalenza non può essere presunta. La connessione legacy viene preservata con ID dedicato incrementale (`<id>-legacy`), ridenominata e migrata nella propria partizione OAuth dedicata isolata (`Partitions/hermes-remote-oauth-conn-<newId>`), garantendo l'accesso ad entrambi gli account in ossequio all'invariante di scope di `AGENTS.md:45-47`.
75. **Trattamento Atomico e Coesivo delle Partizioni Browser (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Durante la migrazione della cartella `Partitions`, il runtime eseguiva un merge ricorsivo file-per-file dei singoli contenuti delle partizioni Electron. Poiché le partizioni contengono database SQLite dei cookie e archivi LevelDB (IndexedDB, LocalStorage, SessionStorage), il merge dei singoli file interni rischiava di corrompere l'archivio LevelDB (conflitti tra MANIFEST e file LOG) e mescolare credenziali di account diversi in violazione di `AGENTS.md:47-48`.
    - *Risoluzione*: La cartella `Partitions` viene ora gestita considerando ogni singola partizione come un'unità di database indivisibile: se la partizione esiste sia nella sorgente che nella destinazione ed entrambe contengono dati, la partizione legacy viene archiviata separatamente come sidecar coeso (`Partitions/<name>.legacy`) e registrata nel manifesto di ripristino, senza mai mescolare i file interni.
76. **Preservazione Permanente del Manifesto e dell'Affordance di Ripristino alla Chiusura della Notifica (`apps/desktop/electron/main.ts`, `apps/desktop/src/store/legacy-migration-recovery.ts`)**:
    - *Problema*: Quando l'utente premeva "Keep Current" o "Keep Legacy", la routine `dismissRecoveryInfo` eliminava fisicamente il file `legacy-migration-recovery.json`. Sebbene gli snapshot persistessero su disco, l'eliminazione del manifesto impediva qualsiasi futuro ripristino tramite interfaccia grafica o API, vanificando la promessa di ripristino garantita da `AGENTS.md:73-78`.
    - *Risoluzione*: `dismissRecoveryInfo` non elimina più il manifesto, ma ne aggiorna lo stato persistendo `dismissed: true` e `dismissedAt`. La notifica di avvio viene silenziata per non disturbare l'utente, ma il manifesto e gli snapshot rimangono intatti e accessibili a tempo indeterminato per qualsiasi futura operazione di ripristino. Inoltre, `restoreLegacyDatabase` implementa una ricerca di fallback sulle directory `.legacy` standard qualora il manifesto non fosse indicizzato.
77. **Preservazione del Sandbox di Chromium nel Riavvio di Ripristino (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Nei gestori di ripristino `restore-legacy-database` e `restore-intervening-database`, il riavvio dell'applicazione veniva eseguito passando gli argomenti a `buildNoSandboxRelaunchArgs`, aggiungendo incondizionatamente il flag `--no-sandbox` e privando il processo di rendering delle protezioni di sicurezza del sandbox anche in assenza di crash GPU.
    - *Risoluzione*: Gli argomenti di riavvio sono stati normalizzati riutilizzando `process.argv.slice(1)` senza l'iniezione non richiesta di `--no-sandbox`, preservando intatta la sandbox di isolamento di Chromium per il codice renderer e guest content.
78. **Disaccoppiamento delle Partizioni OAuth dal Restore Bulk dei Database Utente (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Includendo le partizioni di sessione della directory `Partitions/` nel manifesto di recovery dei database applicativi (`preservedDatabases`), l'azione utente "Restore Legacy Data" eseguiva il ripristino indiscriminato anche dei cookie OAuth (es. `hermes-remote-oauth`) senza ripristinare il file `connections.json`, determinando l'accoppiamento accidentale delle connessioni cloud attive con i cookie dell'account legacy in violazione di `AGENTS.md:47-48`.
    - *Risoluzione*: Le partizioni di sessione in `Partitions/` vengono escluse dal manifesto `preservedDatabases` riservato ai database applicativi (`IndexedDB`, `Local Storage`, `Session Storage`). Le copie legacy delle partizioni in conflitto rimangono preservate come sidecar coesi su disco (`Partitions/<name>.legacy`), ma non vengono scambiate a livello di bulk restore, garantendo il perfetto allineamento tra identità di connessione e credenziali.
79. **Validazione Rigorosa e Whitelist dei Nomi Database nei Gestori IPC (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Il parametro `dbName` accettato dai gestori IPC di restore veniva interpolato senza validazione contro il filesystem, esponendo al rischio di directory traversal (es. sequenze `..`) al di fuori della directory `userData`.
    - *Risoluzione*: È stata implementata una validazione stringente su whitelist che autorizza unicamente `'all'`, i nomi esplicitamente indicizzati nel manifesto di recupero (`manifest.databases`) o i nomi standard fissi di `DATABASE_DIR_NAMES`. Qualsiasi valore non conforme viene rigettato con errore esplicito senza eseguire operazioni su file.
80. **Arresto dell'Avvio su Fallimento della Preparazione della Transazione di Swap/Ripristino (`apps/desktop/electron/main.ts`)**:
    - *Problema*: In `applyPendingLegacyDatabaseRestore()`, se la preparazione della transazione (copia di backup pre-swap, persistenza del file di transazione `.legacy-restore-tx.json` o predisposizione degli snapshot) incontrava un errore (es. disco pieno, lock o permessi insufficienti), l'eccezione veniva catturata dal blocco `catch (err)` più esterno che si limitava a registrare un messaggio di errore in console. Il processo Electron proseguiva così l'avvio, aprendo Chromium e permettendo all'utente di scrivere e modificare i database attivi in presenza di una transazione parziale o interrotta. Al successivo riavvio, `STEP 0` rilevava la transazione incompleta ed eseguiva il recovery sovrascrivendo e cancellando tutte le modifiche apportate dall'utente durante la sessione.
    - *Risoluzione*: Le fasi di inizializzazione e preparazione (Step 1 e Step 2) sono state isolate in un blocco protetto dedicato: in caso di errore, eventuali file temporanei di backup o stage vengono ripuliti, il file di transazione non ancora iniziato viene rimosso, viene mostrato un dialog modale di errore esplicito e l'applicazione viene immediatamente arrestata con `app.exit(1)`. Inoltre, qualsiasi eccezione imprevista catturata nel blocco principale interrompe tassativamente l'avvio prima dell'apertura di Chromium, garantendo che i database attivi non vengano mai aperti in uno stato transazionale compromesso (`AGENTS.md:75-78`).
81. **Preservazione Integrale e Reversibile dello Stato Dismesso nel Ripristino Inverso (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Quando l'utente selezionava "Restore Previous Setup" (`restore-intervening-database`), la procedura scambiava gli snapshot `.intervening` con i database attivi ed eliminava incondizionatamente i backup pre-swap (`db.backupPath`). Poiché i file `.legacy` conservati su disco corrispondevano agli snapshot storici iniziali, tutte le modifiche, sessioni e configurazioni create dall'utente durante l'intervallo temporale in cui i dati legacy sono rimasti attivi venivano distrutte definitivamente senza alcuna possibilità di recupero, e il manifesto veniva eliminato (`fs.rmSync(manifestPath)`).
    - *Risoluzione*: Il ripristino inverso è stato reso simmetrico e privo di perdite: nello Step 2, quando l'azione è `restore-intervening`, il database attivo (contenente i dati legacy arricchiti con le nuove modifiche dell'utente) viene salvato atomicamente nello snapshot `${db.name}.legacy`. Nello Step 5, il manifesto di recovery viene aggiornato e pubblicato con stato `active-preserved-legacy-available`, referenziando i database `.legacy` aggiornati. In questo modo l'utente può alternare liberamente e a tempo indeterminato tra il setup precedente e il setup legacy senza alcuna perdita di dati, in piena coerenza con il principio "server truth is cached, not owned / merge, don't clobber" di `AGENTS.md:59-63`.
82. **Isolamento della Partizione e Conservazione della Configurazione per Connessioni OAuth Migrate (`apps/desktop/electron/main.ts`, `apps/desktop/electron/oauth-partition.ts`, `apps/desktop/electron/connection-registry.ts`)**:
    - *Problema*: Quando una connessione remota con autenticazione OAuth (`kind === 'remote'`, `authMode === 'oauth'`) veniva importata da un'installazione legacy come connessione non primaria con un URL coincidente con il `v1RemoteUrl` della destinazione (`connection.json: remote.url`), la procedura di migrazione creava la partizione privata dedicata (`Partitions/hermes-remote-oauth-conn-<id>`). Tuttavia, a runtime `resolveOauthPartition` applica un'eccezione intenzionale che instrada verso la partizione condivisa `hermes-remote-oauth` qualsiasi connessione coincidente con `v1RemoteUrl`. Inoltre, un tentativo di eliminare `remote.url` da `connection.json` violerebbe il principio di non sovrascrittura dell'intento dell'utente corrente (`AGENTS.md:59-63`). Di conseguenza, la connessione importata avrebbe utilizzato i cookie dell'account della destinazione anziché i propri, violando i confini di isolamento tra account (`AGENTS.md:46-48`).
    - *Risoluzione*: In conformità al principio cardine di `AGENTS.md:46-48` ("Persisted state must declare its scope in its own key"), lo schema `RegistryConnection` e i normalizzatori del registro supportano ora la proprietà esplicita `partition?: string`. In `reconcileConnectionsRegistry`, ogni connessione OAuth migrata dichiara espressamente la propria partizione dedicata (`partition: persist:hermes-remote-oauth-conn-<id>`) senza toccare né alterare in alcun modo la configurazione `connection.json` della destinazione. Parallelamente, `resolveOauthPartition` rispetta in via prioritaria la partizione esplicitamente dichiarata sulla connessione sia tramite `connectionId` che tramite URL matching, garantendo l'assoluto isolamento dei cookie e dei confini di account senza alcuna regressione per la configurazione corrente.
83. **Mantenimento dell'Accessibilità e Riautenticazione delle Connessioni Cloud Migrate (`apps/desktop/electron/main.ts`)**:
    - *Problema*: Quando sia l'installazione corrente che quella legacy disponevano di una sessione OAuth cloud attiva nella partizione condivisa `hermes-remote-oauth`, le connessioni cloud legacy venivano collocate in `currentRegistry.quarantined` e rimosse dall'elenco delle connessioni utilizzabili per prevenire il riutilizzo accidentale dell'account di destinazione. Poiché la nuova partizione isolata è priva di cookie attivi, la connessione compare normalmente nell'elenco delle connessioni del desktop e richiede una riautenticazione esplicita al momento dell'accesso, preservando rigorosamente i confini dell'account senza nascondere la connessione all'utente.
84. **Risoluzione delle Partizioni Esplicite per Connessioni Primarie e URL-Matching (`apps/desktop/electron/oauth-partition.ts`)**:
    - *Problema*: Quando una connessione remota (o cloud isolata) migrata dotata di una proprietà `partition` esplicita veniva designata come primaria (`registry.primary`), le chiamate al resolver `resolveOauthPartition` effettuate per URL anziché per `connectionId` (come avviene internamente nelle chiamate REST e di fetch) saltavano la connessione primaria nel ciclo di corrispondenza per URL, ricadendo sulla partizione legacy condivisa (`persist:hermes-remote-oauth`). Di conseguenza, la fase di autenticazione e le successive richieste HTTP/WebSocket utilizzavano jar di cookie differenti, generando errori 401 e disconnessioni impreviste in contrasto con `apps/desktop/AGENTS.md:46-48`.
    - *Risoluzione*: Aggiornato `resolveOauthPartition`: nel ciclo di corrispondenza per URL, le connessioni che dichiarano una partizione esplicita (`hasExplicitPart`) non vengono più ignorate quando coincidono con `primaryId`. Inoltre, la corrispondenza delle partizioni esplicite viene estesa sia a connessioni di tipo `remote` che `cloud`. In questo modo, sia la risoluzione basata su `connectionId` che quella basata sull'URL di richiesta restituiscono deterministicamente la medesima partizione esplicita, garantendo coerenza e stabilità dello stato di autenticazione.

Poiché `default_home` è genitore di tutti i profili nominati (`~/.hermes/profiles/<name>/`), qualsiasi file legittimo del profilo chiamante veniva classificato erroneamente come appartenente a `default` e respinto con HTTP 403 Forbidden.
    - *Risoluzione*: Aggiornato l'algoritmo di ownership in `profile.py`: se il percorso risiede sotto `profiles_root`, l'appartenenza viene validata unicamente contro l'identificativo del profilo proprietario (`rel.parts[0] == prof_name`). La directory predefinita `default_home` viene verificata solo per file esterni a `profiles_root`, consentendo a ciascun profilo nominato di caricare liberamente i propri file. Validato con unit test `test_named_profile_can_load_own_file`.
200. **Sincronizzazione del Timer di Riproduzione Client-Side Esclusivamente sull'Ack di Inizio Effettivo (`hermes_voice/player.py`)**:
    - *Problema*: (Rilievo Codex Round 11 P2) In modalità client playback, l'invocazione di `get_sentence_audio_wav` impostava immediatamente l'evento `_client_started_event.set()` e considerava la frase in riproduzione. Il worker virtuale faceva avanzare il timer e i segnalibri mentre il client stava ancora scaricando o decodificando l'audio via rete, causando lo sfasamento della timeline o il salto prematuro alla frase successiva.
    - *Risoluzione*: Rimosso l'innesco anticipato di `_client_started_event` da `get_sentence_audio_wav`. Il worker virtuale in `player.py` attende esclusivamente la conferma formale di avvio inviata dal renderer client tramite `POST /playback/ack` con payload `event: "started"`, garantendo sincronizzazione deterministica anche su connessioni lente. Validato con unit test `test_client_playback_does_not_advance_on_audio_fetch`.
201. **Risoluzione Canonica dell'Identità di Profilo Default nel Gestore di Stato (`hermes_voice/server/state.py`)**:
    - *Problema*: (Rilievo Codex Round 12 P2) Quando un tool vocale veniva invocato per primo su un profilo predefinito senza specificare il parametro `profile`, `get_assistant()` ricavava il nome del profilo dal basename della directory genitore (`prof_dir.parent.name`), impostandolo a `.hermes` (o `hermes`) anziché `default`. Successivamente, la verifica di ownership dei percorsi scambiava la home predefinita per un profilo estraneo, rigettando i file PDF legittimi ivi residenti (inclusi i file caricati). Poiché l'istanza veniva memorizzata nella cache in memoria, l'errore si propagava a tutte le richieste successive.
    - *Risoluzione*: Aggiornata la risoluzione in `state.py`: se `prof_dir.parent.resolve()` coincide con la home predefinita restituita da `_get_default_hermes_home()`, il profilo viene forzato deterministicamente a `"default"`. Se risiede in `profiles_root`, l'identificativo viene estratto dai segmenti relativi del percorso (`rel_parts[0]`). L'assistente viene inizializzato con il nome profilo autentico, garantendo che i documenti nella home predefinita siano sempre riconosciuti e validati con successo.
202. **Disponibilità del Plugin Desktop Bundled Tramite Percorso di Discovery Nativo (`apps/desktop/src/plugins/voice-document-assistant/plugin.js`)**:
    - *Problema*: (Rilievo Codex Round 12 P2) In installazioni dal codice sorgente o checkout di sviluppo, l'estensione desktop risiedeva unicamente sotto `plugins/voice-document-assistant/desktop/plugin.js`. Il loader Electron delle estensioni desktop modali (`apps/desktop/src/contrib/plugins.ts`) esegue la glob statica su `src/plugins/*/plugin.{js,ts,tsx}` per i plugin distribuiti con l'applicazione (come `kanban` e `radio`), mentre `reconcileUnifiedDesktopHalves` scansiona solo le directory `plugins/` all'interno della `HERMES_HOME`. Di conseguenza, in assenza di un'installazione manuale separata del pacchetto nella home utente, il pannello del plugin vocale non appariva nel desktop client.
    - *Risoluzione*: Registrato il plugin desktop in `apps/desktop/src/plugins/voice-document-assistant/plugin.js`, inserendolo nel percorso supportato di discovery dei plugin bundled di Electron. Il frontend React viene compilato e integrato nativamente all'avvio dell'applicazione desktop, garantendo la disponibilità immediata del pannello vocale sia in esecuzione da sorgente sia nelle build impacchettate.
203. **Scarto Immediato dei Payload Audio Asincroni Obsoleti per Prevenire Desincronizzazioni e Sovrapposizioni (`desktop/plugin.js`, `apps/desktop/.../plugin.js`, `dashboard/dist/index.js`)**:
    - *Problema*: (Rilievo Codex Round 13 P1) Nelle interfacce reactive del desktop client e della web dashboard, quando il polling o il fetch di rete di un blob audio (`/playback/sentence/{index}/audio`) è lento o ritardato, l'utente poteva compiere azioni immediate come mettere in pausa, premere stop, o navigare a un altro documento/pagina. Al completamento del fetch in background, l'audio stale veniva comunque passato a `new Audio(...).play()`, provocando la riproduzione inattesa di audio fuori contesto, desincronizzazione della timeline o sovrapposizioni sonore incontrollate.
    - *Risoluzione*: Introdotto un contatore generazionale di polling (`pollGenRef` / `currentGen`), un flag di unmount/disposal (`disposed`) e una convalida atomica di freschezza prima dell'avvio della riproduzione audio. Se lo stato di riproduzione cambia, la connessione viene interrotta o la generazione corrente non corrisponde a quella della richiesta, il blob audio in volo viene scartato immediatamente senza emettere suoni. Validato con typecheck Electron e suite Vitest.
204. **Tracciamento Composito dell'Identità di Riproduzione Documento-Frase (`desktop/plugin.js`, `apps/desktop/.../plugin.js`, `dashboard/dist/index.js`)**:
    - *Problema*: (Rilievo Codex Round 13 P1) Il controllo di deduplicazione della riproduzione utilizzava unicamente l'indice numerico di frase (`lastPlayedSentenceRef = sentence_index`). Quando l'utente passava da un documento a un altro che si trovava allo stesso indice di frase (tipicamente la frase 0), o effettuava upload di un nuovo PDF mentre era attiva una sessione precedente, il renderer client scambiava la nuova richiesta per una duplicazione della precedente, non riproducendo l'audio o riproducendo frammenti incoerenti.
    - *Risoluzione*: Sostituito il tracciamento numerico semplice con una chiave composita documento-frase (`${targetDocId}:${sentence_index}`). Il riferimento `lastPlayedTargetRef` viene resettato deterministicamente su cambio documento, upload di nuovo file, arresto della riproduzione e operazioni di seek. In tal modo ogni combinazione documento-frase possiede un'identità univoca garantendo la corretta esecuzione di ogni transizione.
205. **Avanzamento del Flusso di Riproduzione Client Esclusivamente su Segnale di Avanzamento e Completamento Ricevuto (`hermes_voice/player.py`)**:
    - *Problema*: (Rilievo Codex Round 13 P2) Nella modalità client playback di `player.py`, il server simulava l'avanzamento temporale tramite un timer wall-clock virtuale nel thread di background. Se il client web o desktop subiva rallentamenti di decodifica, buffering di rete o sospensione della finestra di rendering (throttling di background), il timer virtuale del server continuava ad avanzare autonomamente, saltando frasi e memorizzando posizioni di segnalibro fittizie per porzioni di testo mai effettivamente ascoltate dall'utente.
    - *Risoluzione*: Eliminata qualsiasi stima o simulazione basata su clock virtuale in modalità client playback. Il server sincronizza `_sample_offset` unicamente sugli eventi di telemetria periodica (`event: "progress"`) emessi dal player audio client, e attende indefinitamente l'ack esplicito di completamento della frase (`event: "ended"` via `POST /playback/ack`) prima di preparare o sbloccare la frase successiva. Se il client stalla o viene messo in pausa, il server arresta determinatamente il flusso senza drift temporale. Validato con la suite di test del plugin.
206. **Ripristino e Riprova Immediata del Fetch Audio Frase su Discard o Errore Asincrono (`desktop/plugin.js`, `apps/desktop/.../plugin.js`, `dashboard/dist/index.js`)**:
    - *Problema*: (Rilievo Codex Round 14 P1) Se la sintesi audio remota falliva temporaneamente o l'effetto React veniva riavviato (es. al cambio o refresh di `docData`) mentre un fetch `/audio/sentence/{idx}` era ancora in volo, la richiesta precedente veniva scartata ma `lastPlayedTargetRef` conteneva già la chiave della frase corrente. I successivi cicli di polling ritenevano erroneamente la frase già riprodotta e non tentavano più il download, lasciando la riproduzione client bloccata all'infinito in attesa di un acknowledgement che non sarebbe mai arrivato.
    - *Risoluzione*: Separato il tracciamento del fetch in corso (`fetchingTargetRef`) da quello della riproduzione attiva (`lastPlayedTargetRef`). `lastPlayedTargetRef` viene impostato unicamente dopo che l'istanza `Audio` è stata creata, configurata ed avviata con successo (`audio.play()`). Se il fetch viene scartato per cambio stato, abortito per unmount o fallisce con errore di rete, `fetchingTargetRef` viene ripulito immediatamente e `lastPlayedTargetRef` viene azzerato in cleanup, permettendo al polling successivo di riprovare automaticamente la sintesi della frase senza stallo. Validato con typecheck Electron e suite Vitest.
207. **Risoluzione Dinamica del Provider e dell'Endpoint di Inferenza Locale Configurato (`hermes_voice/model_router.py`)**:
    - *Problema*: (Rilievo Codex Round 14 P2) Quando l'utente configurava durante il setup o via CLI un provider locale personalizzato (LM Studio, vLLM, o un server Ollama su porta/indirizzo non standard come `127.0.0.1:11435` o `127.0.0.1:1234/v1`), il `ModelRouter` dell'assistente documentale leggeva unicamente il nome del modello da `config.yaml`, mantenendo cablato il provider `ollama` e l'URL predefinito `127.0.0.1:11434`. Di conseguenza, l'assistente non era in grado di rispondere alle domande sui documenti e andava in errore a meno che non fosse in esecuzione una seconda istanza separata di Ollama sulla porta canonica.
    - *Risoluzione*: Aggiornato il costruttore di `ModelRouter` per risolvere sia il provider (`model.provider`) sia l'endpoint effettivo (`model.base_url`) salvati nella configurazione di NOEMETRA. Se è configurato un provider locale OpenAI-compatibile (LM Studio, vLLM, custom), il router imposta automaticamente `default_provider = "openai_compatible"` e indirizza le richieste all'endpoint configurato; se è configurato Ollama su una porta custom, normalizza e adotta l'URL specificato. Validato con unit test dedicati in `test_router.py`.
208. **Esecuzione Asincrona Fuori dall'Event Loop dei Metodi di Controllo Riproduzione (`hermes_voice/server/api.py`)**:
    - *Problema*: (Rilievo Codex Round 14 P2) Gli endpoint REST di controllo della riproduzione (`POST /playback/play`, `/pause`, `/resume`, `/stop`, `/seek`) invocavano direttamente i metodi sincroni dell'assistente nel thread principale di FastAPI. Poiché durante la sintesi vocale i metodi `play()`, `pause()` e `stop()` possono attendere il rilascio o il join del thread worker per diversi secondi (fino al timeout di 10s), chiamarli direttamente sull'event loop causava il blocco totale del gateway, ritardando tutte le richieste concorrenti e la gestione dei socket.
    - *Risoluzione*: Tutti i metodi di riproduzione e seek (`assistant.play`, `assistant.pause`, `assistant.resume`, `assistant.stop`, `assistant.seek_sentence`, `assistant.seek_page`) sono ora delegati a un worker thread dedicato tramite `await asyncio.to_thread(...)`, replicando il modello non bloccante già adottato con successo per il caricamento dei PDF. Validato con la suite `test_server_api.py`.
209. **Convalida dell'Ownership e Isolamento dei Profili Basata sui Percorsi Fisici Canonici (`hermes_voice/server/api.py`, `profile.py`)**:
    - *Problema*: (Rilievo Codex Round 15 P1) Quando una sessione nativa utilizzava una directory home personalizzata (`HERMES_HOME` o ticket native principal) il cui basename coincideva casualmente con il nome di un profilo standard (es. `/tmp/custom/noemetra`), `_resolve_authorized_context` deduceva il nome del profilo direttamente dal basename della cartella (`resolved.name`), assegnando alla sessione l'identità del profilo nominato. Successivamente, `validate_path_profile_ownership` consentiva l'accesso ai file PDF riservati in `~/.hermes/profiles/noemetra` perché il confronto controllava unicamente l'uguaglianza dei nomi di stringa, violando l'isolamento dei dati sancito da AGENTS.md:13.
    - *Risoluzione*: Aggiornato l'algoritmo di autorizzazione in `api.py` per legare `bound_profile` al nome di un profilo solo se la directory fisica coincide effettivamente con la directory canonica (`resolved.parent == prof_root` o `_resolve_profile_home(name) == resolved`). In `profile.py`, `validate_path_profile_ownership` confronta ora le directory home fisiche risolte (`caller_home != expected_home`) anziché i semplici nomi testuali, bloccando con HTTP 403 / PermissionError qualunque tentativo di accesso a file di profili nominati da home esterne o custom. Validato con unit test `test_custom_home_matching_profile_basename_cannot_access_named_profile_files`.
210. **Blocco dei Reindirizzamenti Remoti Incontrollati nelle Richieste di Inferenza Locale (`hermes_voice/model_router.py`)**:
    - *Problema*: (Rilievo Codex Round 15 P1) Se un server o proxy di inferenza locale configurato restituiva un reindirizzamento HTTP 301, 302, 307 o 308 verso un host esterno o remoto, `requests.post` seguiva automaticamente il reindirizzamento inoltrando l'intero prompt (contenente estratti riservati del documento) all'endpoint remoto anche in assenza del consenso esplicito dell'utente (`allow_remote=False`).

Introdotta l'intercettazione di qualsiasi stato di reindirizzamento con validazione preventiva dell'header `Location` tramite `urljoin` e `is_local_endpoint`: se la destinazione è remota e `allow_remote=False`, la richiesta viene bloccata immediatamente sollevando `PermissionError` con notifica di violazione della privacy. Validato con unit test `test_privacy_guard_blocks_remote_redirect_from_local_ollama` e `test_privacy_guard_blocks_remote_redirect_from_local_openai_compatible`.
211. **Configurazione Integrale ed Eredità dei Parametri per Provider Remoti Autorizzati (`hermes_voice/model_router.py`)**:
    - *Problema*: (Rilievo Codex Round 15 P2) Quando l'utente configurava un provider remoto riconosciuto (OpenAI, Anthropic, OpenRouter) ed abilitava esplicitamente l'accesso remoto (`allow_remote=True`), `ModelRouter` non estraeva l'endpoint (`model.base_url`), le credenziali (`api_key` o variabili d'ambiente dedicate come `ANTHROPIC_API_KEY`) né il modello prescelto dal file di configurazione, ripiegando sempre su valori cablati di default (`https://api.openai.com/v1` e `gpt-4o-mini`). Di conseguenza, le richieste a provider remoti fallivano per autenticazione mancante o venivano instradate al provider errato.
    - *Risoluzione*: Implementata l'estrazione completa dei parametri del provider remoto da `config.yaml` ed environment in `ModelRouter.__init__` (`remote_base_url`, `remote_api_key`, `model`). In `generate()`, il router utilizza l'endpoint canonico, le credenziali specifiche e il modello configurato per il provider selezionato (`anthropic`, `openrouter`, `openai`). Validato con unit test `test_remote_provider_settings_populated_from_config`.
